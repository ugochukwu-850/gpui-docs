When you read GPUI code you keep meeting things that have no definition you can find: where is `px_2()` declared? What does `#[derive(IntoElement)]` actually add? This page answers those questions. The answers live in `crates/gpui_macros` (3,631 lines), read from commit `b5cd310b`.

## What you'll learn

- What a procedural macro is, and which three kinds `gpui_macros` has.
- What `#[derive(IntoElement)]`, `#[derive(Action)]` and `actions!` generate.
- Why `div().px_2().w_full().mt_4()` works without anyone writing thousands of methods by hand.
- What `#[gpui::test]` expands to.

:::note[Advanced]
This page is for readers who are comfortable with Rust traits and who have seen `#[derive(...)]` before. You do not need to have written a macro. If you only want to *use* these macros, the guides ([Actions and keybindings](/guides/actions-and-keybindings/), [Testing](/guides/testing/), [Styling](/guides/styling/)) are enough.
:::

:::tip[In short]
1. A *procedural macro* is Rust code that runs at compile time and writes more Rust code. `gpui_macros` holds all of GPUI's.
2. `#[derive(IntoElement)]` makes a component usable as a child. `#[derive(Action)]` makes a command that can be bound to keys. The style helpers generate the Tailwind-like methods on `Styled`.
3. `actions!` is **not** a procedural macro. It is a plain `macro_rules!` in `crates/gpui/src/action.rs`.
:::

## How to read this page

Rust has three kinds of procedural macro, and you can tell them apart by how they are written:

- A **derive macro** is written `#[derive(Name)]` on a struct. It adds an `impl` block for you.
- An **attribute macro** is written `#[name]` or `#[name(args)]` on an item. It can rewrite the item it is attached to (for example `#[gpui::test]` on a function).
- A **function-like macro** is written `name!(...)`. It expands in place (for example `padding_style_methods!()`).

The entry point `src/gpui_macros.rs` is only a list of `#[proc_macro*]` functions that forward to one file each. Here is every macro, where its code lives, and how `gpui` re-exports it:

| Macro | Kind | Source file | Re-exported from `gpui` as |
| --- | --- | --- | --- |
| `Action` | derive (attribute `action`) | `derive_action.rs` | `gpui::Action` (also the trait of the same name) |
| `register_action!` | function-like | `register_action.rs` | `gpui::register_action` |
| `IntoElement` | derive | `derive_into_element.rs` | `gpui::IntoElement` (also the trait) |
| `Render` | derive, `#[doc(hidden)]` | `derive_render.rs` | `gpui::Render` (also the trait) |
| `AppContext` | derive (attribute `app`) | `derive_app_context.rs` | `gpui::AppContext` (also the trait) |
| `VisualContext` | derive (attributes `window`, `app`) | `derive_visual_context.rs` | `gpui::VisualContext` (also the trait) |
| `#[gpui::test]` | attribute | `test.rs` | `gpui::test` |
| `#[gpui::bench]` | attribute | `bench.rs` | `gpui::bench` |
| `#[gpui::property_test]` | attribute | `property_test.rs` | `gpui::property_test` |
| `style_helpers!`, `visibility_style_methods!`, `margin_style_methods!`, `padding_style_methods!`, `position_style_methods!`, `overflow_style_methods!`, `cursor_style_methods!`, `border_style_methods!`, `box_shadow_style_methods!` | function-like | `styles.rs` | the last eight via `gpui::*` (from `styled.rs`); `style_helpers!` is `#[doc(hidden)]` |
| `#[derive_inspector_reflection]` | attribute, only with `inspector` feature or `debug_assertions` | `derive_inspector_reflection.rs` | `gpui_macros::derive_inspector_reflection` (used as `gpui_macros::...` in `styled.rs`) |

## What you write, and what it becomes

Here is the short version. The sections below show the generated code in full.

```text
#[derive(IntoElement)] struct Foo;           -> impl IntoElement for Foo { type Element = ViewElement<Foo>; .. }
#[derive(Action)] struct Save;               -> impl Action for Save + inventory::submit!(MacroActionBuilder(..))
actions!(editor, [Undo, Redo]);              -> struct Undo; struct Redo; each #[derive(Action)] #[action(namespace = editor)]
div().px_4()                                 -> Styled::px_4, generated by padding_style_methods!/style_helpers!
#[gpui::test] async fn t(cx: &mut TestAppContext) -> #[test] fn t() { gpui::run_test(.., |dispatcher, _| { .. block_test(__t(&mut cx)) .. }) }
```

`gpui_macros` has one Cargo feature, `inspector = []`, enabled by `gpui`'s `inspector` feature.

## `#[derive(IntoElement)]`

For a type that implements `RenderOnce`. Source: `derive_into_element.rs` (30 lines). It generates:

```rust
impl<generics> gpui::IntoElement for MyComponent<generics> where ... {
    type Element = gpui::ViewElement<Self>;

    #[track_caller]
    fn into_element(self) -> Self::Element { gpui::ViewElement::new(self) }

    #[track_caller]
    #[inline(never)]
    fn into_any_element(self) -> gpui::AnyElement { gpui::Element::into_any(self.into_element()) }
}
```

`ViewElement<V: View>` (`gpui/src/view.rs`) is the element that renders a `View`. Every `RenderOnce` type is a `View` through the blanket `impl<T: RenderOnce> View for T` with `entity_id() == None`, so the derived impl makes a component embed as a stateless subtree. In plain words: `render` runs each frame during `request_layout`, under an element-id scope named after the type (`request_layout_component`, `with_id(ElementId::from(type_name))`).

`#[track_caller]` records the construction site for the inspector (`source_location`). This is the macro behind almost every `#[derive(IntoElement)]` in the `ui` crate; see [A real component library](/codebase/reading-zed-ui-crate/).

Entities implementing `Render` do not use this derive: `impl<V: Render> IntoElement for Entity<V>` is written by hand in `view.rs`.

## `#[derive(Render)]` (hidden)

`derive_render.rs`: expands to a `Render` impl whose `render` returns `gpui::Empty`. The only use found in the checkout is a compile test (`crates/gpui_macros/tests/render_test.rs`). It is `#[doc(hidden)]`, although `gpui.rs` re-exports it.

## `#[derive(Action)]`, `actions!` and `register_action!`

`derive_action.rs` (211 lines) parses `#[action(...)]` arguments: `name = "..."`, `namespace = ident`, `no_json`, `no_register`, `deprecated_aliases = [...]`, `deprecated = "..."`; doc comments on the struct are concatenated into the action's documentation. It rejects `name` values containing `::` with `"in #[action] attribute: `name = \"{name}\"` must not contain `::`, also specify `namespace` instead"`. The full name is `namespace::Name` (or only `Name` when no namespace is given).

It generates `impl gpui::Action for T`:

| `Action` method | Generated |
| --- | --- |
| `name()` / `name_for_type()` | the full-name string |
| `partial_eq(&dyn Action)` | `action.as_any().downcast_ref::<Self>().map_or(false, |a| self == a)` (so the type needs `PartialEq`) |
| `boxed_clone()` | `Box::new(self.clone())` (needs `Clone`) |
| `build(value)` | unit struct: `Ok(Box::new(Self))`; else `serde_json::from_value::<Self>(value)` (needs `Deserialize`); with `no_json`: always `Err("{name} cannot be built from JSON")` |
| `action_json_schema(generator)` | `Some(schemars JsonSchema)` unless unit struct or `no_json` (then `None`) |
| `deprecated_aliases()`, `deprecation_message()`, `documentation()` | the corresponding attribute values |

and, unless `no_register`, the registration code from `register_action.rs`:

```rust
impl MyAction {
    #[doc(hidden)]
    fn __autogenerated() {
        fn __gpui_actions_builder_myaction() -> gpui::MacroActionData {
            gpui::MacroActionData {
                name: <MyAction as gpui::Action>::name_for_type(),
                type_id: ::std::any::TypeId::of::<MyAction>(),
                build: <MyAction as gpui::Action>::build,
                json_schema: <MyAction as gpui::Action>::action_json_schema,
                deprecated_aliases: ..., deprecation_message: ..., documentation: ...,
            }
        }
        gpui::private::inventory::submit! { gpui::MacroActionBuilder(__gpui_actions_builder_myaction) }
    }
}
```

At startup `ActionRegistry::load_actions` iterates `inventory::iter::<MacroActionBuilder>` (see [input internals](/codebase/input-and-dispatch-internals/)). `register_action!(Type)` emits only the registration block, for types that implement `Action` by hand.

The `actions!` macro is **not** a proc macro. It is a `macro_rules!` in `gpui/src/action.rs` that expands each name to a unit struct deriving `Clone, PartialEq, Default, Debug` and `gpui::Action`, adding `#[action(namespace = $namespace)]` when a namespace is given.

## `#[derive(AppContext)]` and `#[derive(VisualContext)]`

For wrapper types that hold a `&mut App` (and a `&mut Window`) and want to *be* a context. Mark the fields with attributes:

```rust
#[derive(AppContext)]
struct MyCx<'a> { #[app] app: &'a mut gpui::App }

#[derive(VisualContext)]
struct MyVisualCx<'a, 'b> { #[app] app: &'a mut gpui::App, #[window] window: &'b mut gpui::Window }
```

The derives generate delegating implementations of the `AppContext` / `VisualContext` traits (`gpui.rs`): every method (`new`, `reserve_entity`, `insert_entity`, `update_entity`, `as_mut`, `read_entity`, `update_window`, `with_window`, `read_window`, `background_spawn`, `read_global`) forwards to `self.<app field>`. The `VisualContext` derive also sets `type Result<T> = T`. If the attribute is missing, the derive emits `compile_error!("Derive must have an #[app] attribute to detect the &mut App field")` (and `#[window]` for `VisualContext`). The doctests in `gpui_macros.rs` pin this behaviour with `compile_fail` examples. `tests/derive_context.rs` exercises it.

## Test macros

### `#[gpui::test]`

`test.rs` (347 lines). It renames your function to `__your_fn`, strips its attributes, and generates a `#[test] fn your_fn()` that calls `gpui::run_test(iterations, &[seeds], retries, &mut |dispatcher, _seed| { ... }, on_failure)`.

Accepted arguments: `seed = N`, `seeds(a, b, c)`, `iterations = N`, `retries = N`, `on_failure = "path::to::fn"`. Accepted function parameters, matched by the last segment of their type path:

| Parameter type | Provided as |
| --- | --- |
| `&mut TestAppContext` / `&TestAppContext` | `gpui::TestAppContext::build(dispatcher.clone(), Some(stringify!(fn_name)))` |
| `&mut App` (sync tests only) | A `TestAppContext` whose `app.borrow_mut()` guard is passed in |
| `StdRng` | `rand::SeedableRng::seed_from_u64(_seed)` |
| `BackgroundExecutor` (async tests) | `gpui::BackgroundExecutor::new(Arc::new(dispatcher.clone()))` |

Any other parameter yields the error `"invalid function signature"`. For `async fn` the body runs through `ForegroundExecutor::new(exec).block_test(inner(args))`. After the test, the teardown block does `cx.run_until_parked(); cx.update(|cx| { cx.background_executor().forbid_parking(); cx.quit(); }); cx.run_until_parked(); drop(cx);` and `dispatcher.drain_tasks()`. Environment variables `SEED` and `ITERATIONS` override seeds and iteration counts (`gpui/src/seeds.rs`, `calculate_seeds`).

The runtime half lives in `gpui/src/test.rs` (`run_test`, `run_test_once` which creates a `TestDispatcher::new(seed)` and calls `scheduler.end_test()`).

### `#[gpui::property_test]`

`property_test.rs` (273 lines): a variant built on `proptest`. Extra argument `#[strategy = ...]` on parameters; `StdRng` parameters are explicitly rejected because they break shrinking. It wraps the user function into a proptest property that takes a `__seed: u64` generated by `::gpui::seed_strategy()` and runs the body through `::gpui::run_test_once(__seed, ...)`. Requires `proptest` (a `test-support` dependency of `gpui`).

### `#[gpui::bench]`

`bench.rs` (304 lines): generates Criterion benchmarks that run with a GPUI context. Arguments: `inputs`, `input_name`, `group`, `sample_size`, `fps`, and the same `seed`/`seeds`/`iterations` as tests (a benchmark with a `StdRng` parameter runs once per seed, named `<name>/seed-<seed>`). The crate using it needs `criterion` and `gpui_platform` (with `test-support`) and gpui's `bench` feature, per the macro's documentation.

## Style helper macros

These are why `div().px_2().w_full().mt_4()` exists without anyone having written thousands of methods by hand. They are **function-like proc macros invoked inside the `Styled` trait definition** (`crates/gpui/src/styled.rs`):

```rust
pub trait Styled: Sized {
    fn style(&mut self) -> &mut StyleRefinement;

    gpui_macros::style_helpers!();
    gpui_macros::visibility_style_methods!();
    gpui_macros::margin_style_methods!();
    gpui_macros::padding_style_methods!();
    gpui_macros::position_style_methods!();
    gpui_macros::overflow_style_methods!();
    gpui_macros::cursor_style_methods!();
    gpui_macros::border_style_methods!();
    gpui_macros::box_shadow_style_methods!();
    // ... hand-written methods follow
}
```

`styles.rs` (1,417 lines) builds method sets from tables of **prefixes** and **suffixes** and emits two shapes of method per combination:

- *custom value*: `fn mt(mut self, length: impl Clone + Into<gpui::DefiniteLength>) -> Self` (`generate_custom_value_setter`);
- *predefined*: `fn mt_4(mut self) -> Self` (and `_neg` variants for margins/insets) that sets the field(s) to a fixed length with a doc string like `"4px (0.25rem)"` (`generate_predefined_setter`).

Prefix tables (from `styles.rs`): margin `m mt mb my mx ml mr`; padding `p pt pb px py pl pr`; inset `inset top bottom left right`; box `w h size min_w min_h min_size max_w max_h max_size gap gap_x gap_y`; corner `rounded rounded_t rounded_b rounded_l rounded_r rounded_tl rounded_tr rounded_bl rounded_br`; border `border border_t border_b border_l border_r border_x border_y`. Suffix values include `0`, `0p5`, `1`, `1p5`, ..., `96`, `112`, `128`, `auto`, `px`, `full`, fractions such as `1_2`, `1_3`, `2_3`, `1_4`, `3_4`, ..., and for corners `none xs sm md lg xl 2xl 3xl full`. Each carries a link to the matching Tailwind documentation in its doc comment.

Smaller macros are written out in full with `quote!`: `visibility_style_methods!` -> `visible()`, `invisible()`; `position_style_methods!` -> `relative()`, `absolute()`; `overflow_style_methods!` -> `overflow_hidden`, `overflow_x_hidden`, `overflow_y_hidden`; `cursor_style_methods!` -> `cursor(CursorStyle)` plus about two dozen named cursors (`cursor_pointer`, `cursor_text`, `cursor_not_allowed`, `cursor_grab`, `cursor_col_resize`, ...); `border_style_methods!` -> `border_color(..)` plus border width setters; `box_shadow_style_methods!` -> `shadow(Vec<BoxShadow>)`, `shadow_none`, `shadow_2xs` ... `shadow_2xl`.

All of these accept an optional `{ visibility: <vis> }` argument (see `StyleableMacroInput`). Without it the methods are private to the module, which is why `ui`'s `Facepile` writes:

```rust
gpui::padding_style_methods!({
    visibility: pub
});
```

to get public padding helpers on its own type while implementing a manual `fn style(&mut self) -> &mut StyleRefinement`.

## `#[derive_inspector_reflection]`

`derive_inspector_reflection.rs` (305 lines; "generated using Zed Agent with Claude Opus 4" according to its file header). Applied to a **trait**, it scans for methods of the shape `fn name(self) -> Self` (or `mut self`) with exactly one parameter, including those with default bodies, expanding known macros inside the trait first (that is how the methods created by the style macros above are seen). It returns the trait unchanged plus a module named `<snake_case_trait>_reflection`:

```rust
pub mod styled_reflection {
    pub fn methods<T: Styled + 'static>() -> Vec<gpui::inspector_reflection::FunctionReflection<T>>;
    pub fn find_method<T: Styled + 'static>(name: &str) -> Option<gpui::inspector_reflection::FunctionReflection<T>>;
}
```

`FunctionReflection` (`gpui/src/inspector.rs`) carries `name`, a type-erased `function` wrapper, and the method's doc comment. The in-app inspector uses it to list and invoke builder methods like `.px_2()` at runtime against a `Styled` element. It is applied to `Styled` in `gpui/src/styled.rs` and to `StyledExt` in `ui/src/traits/styled_ext.rs`, under `cfg_attr(all(any(feature = "inspector", debug_assertions), not(rust_analyzer)), ...)` in `gpui` and `cfg_attr(all(debug_assertions, not(rust_analyzer)), ...)` in `ui`. The `not(rust_analyzer)` guard is explained in a comment: rust-analyzer takes up to 10 seconds to expand it. Inside the `gpui` crate the generated code refers to `crate::inspector_reflection`, elsewhere to `::gpui::inspector_reflection`, decided by checking `CARGO_PKG_NAME == "gpui"` in the macro.

## Try it yourself

These are reading exercises. None changes the repository.

1. Open `crates/gpui_macros/src/gpui_macros.rs`. Count the `#[proc_macro*]` functions and match each to a row in the table above.
2. Open `derive_into_element.rs` (30 lines). Compare the `quote!` block with the code shown under "`#[derive(IntoElement)]`" on this page.
3. Open `crates/ui/src/components/label/label.rs` and find `#[derive(IntoElement)]`. Then find the `impl RenderOnce for Label`. Why does the derive only work on a type that implements `RenderOnce`? (Hint: `ViewElement<V: View>` and the blanket `impl<T: RenderOnce> View for T`.)
4. In `crates/gpui/src/action.rs`, find the `actions!` `macro_rules!`. Write out by hand what `actions!(editor, [Undo])` becomes.
5. Open `styles.rs` in `gpui_macros` and find the prefix table for padding (`p pt pb px py pl pr`). Which function turns a prefix and a suffix into `fn px_4(mut self) -> Self`?
6. Open `crates/gpui/src/styled.rs` and find the `gpui_macros::padding_style_methods!();` line. That single line produces about twenty methods.
7. Look at `crates/gpui_macros/tests/` and `crates/gpui/tests/action_macros.rs`. Which macro behaviours are pinned by tests?
